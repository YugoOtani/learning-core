# 目的

実装したい内容を、`mini-impl`で1件ずつ実行できるmicrotaskの列へ分解する。

このスキルでは実装しない。
実装手順案を1つだけ提示する。

# microtaskの基準

microtaskは、コード量ではなく

**人間が1回の判断で承認できる最小の設計上のコミットメント**

とする。

以下を満たす単位を選ぶ。

- 目的が1つ
- 完了状態が明確
- 独立して確認できる
- 実装後も意味のある状態になる
- 次のmicrotaskを先取りしない

コード量の目安は10-30行程度であるが、判断のしやすさを優先する。

関数作成、ファイル編集などの機械的な作業単位では分割しない。

# 手順

## 1. 現在状態を確認する

妥当なmicrotaskへ分解するために必要な範囲でコードを読む。
ここは省略しない。

確認するもの:

- 既存の責務分割
- データや制御の流れ
- 利用できる既存API
- 関連テスト
- プロジェクトルール

## 2. 実装内容を分解する

要求された最終状態までを、依存関係に沿ってmicrotaskへ分解する。

以下は避ける。

- 関係のないリファクタリング
- 将来のためだけの抽象化
- 不要な汎用化
- 過剰なエラーハンドリング
- テスト追加を独立したmicrotaskにすること
- コード構造だけを理由とした細かすぎる分割

仕様・設計・実装上の判断が必要な箇所は勝手に確定せず、microtask内に判断点として明示する。

## 3. 手順案を提示する

実装順に箇条書きで1案だけ提示する。

各microtaskは最大3行程度とし、以下が分かるようにする。

- どのコンポーネントを変更するか
- 何をできるようにするか
- 必要なら判断が必要な点

例:

- `ApiClient`でレスポンスを既存の`User`モデルへ変換する。
  既存の取得処理は変更せず、変換責務だけを追加する。

- `UserRepository`から変換済みの`User`を取得できるようにする。
  キャッシュを持たせるかはこの段階では決めず、既存構造を維持する。

- 取得した`User`を既存のViewModelへ渡して画面に表示する。
  新しい状態管理方式は導入しない。

説明、総括、別案は原則として追加しない。

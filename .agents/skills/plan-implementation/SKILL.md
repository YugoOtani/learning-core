# 目的

実装を開始する前に対象コードを確認し、

- 何のために変更するか
- どの実装要素を追加・変更・削除するか
- それらの責務とデータの受け渡しをどう変えるか
- コンポーネント間の境界をどう変えるか
- 主要な境界のシグニチャをどうする想定か

を、実装者が短時間で理解できる粒度に整理する。

# 入力

対象タスクの以下を確認する。

- `.ai/features/<feature-name>/tasks/<task-name>/task.md`
- `AGENTS.md`
- 関連する機能仕様
- `docs/coding-guidelines.md`
- `docs/test-guidelines.md`
- 関連する既存コード
- 関連する既存テスト
- 既存の抽象化・architecture boundary

タスク記述だけから実装方針を推測しない。

# 基本方針

Planでは、

**「何のために」＋「実装上何を変えるか」**

を基本単位とする。

実装上の変更は、実装者が作業内容を具体的に把握できる形で列挙する。
型や関数の定義・変更、引数や戻り値の変更、データの受け渡し、状態の保持・更新、
表示や出力の構成など、タスクを実現するために必要な変更を洗い出す。
変更後の振る舞いだけを述べて、実装で何を追加・変更するかを読み手に補わせない。

例:

- VSCode APIへの依存をアプリケーション側から切り離すため、`ConfigFileEventSource` インターフェースを導入する
- 変更対象を呼び出し側へ伝えるため、`onDidChange` のlistenerへ `uri` を渡す
- 設定変更を表示へ反映するため、変更通知を受けてレビュー状態を再読込する

ファイル単位や実装順序ではなく、
意味のある変更単位で整理する。

# 手順

## 1. 対象コードを確認する

今回の変更に関係するコードを確認する。

最低限、以下を把握する。

- 現在どの責務がどこにあるか
- 関係する主要な型・関数・インターフェース
- データやイベントがどこからどこへ渡るか
- 既存の依存関係
- 今回変更する境界

必要以上にコードベース全体を調査しない。

## 2. 変更の目的を特定する

単に「何を追加するか」ではなく、

**なぜその変更が必要なのか**

を確認する。

例えば、

「インターフェースを追加する」

ではなく、

「VSCode APIへの依存をアプリケーション側から切り離すため、インターフェースを追加する」

と捉える。

理由を必要以上に深掘りせず、
実装判断を理解するのに必要な範囲だけ記述する。

## 3. 意味のある変更単位に分ける

必要な実装作業を具体的な変更事項へ展開してから、
実装者が理解しやすい変更単位にまとめる。
同じ意味・変更種別の作業だけをまとめ、異なる作業を抽象的な目的の箇条書きに隠さない。
必要な変更をすべて列挙することを優先し、箇条書きの数を少なくするために異なる作業を統合しない。

良い例:

- 呼び出し元から変更対象を渡せるようにするため、関数の引数へ `uri` を追加し、呼び出し箇所から値を渡す
- 設定ファイルの変更を検知するため、イベント購読関数を定義し、変更時に購読者へURIを通知する
- 取り込んだ値を画面へ渡せるようにするため、状態を保持する場所を追加し、入力画面から表示コンポーネントへ値を渡す

避ける例:

- `foo.ts` を変更する
- `bar.ts` を変更する
- 30行目を修正する

ファイルは変更箇所を特定する補助情報として扱い、
Planの主語にはしない。

## 4. 主要な想定シグニチャを示す

新規または変更される主要な境界については、
実装前時点の想定シグニチャをPlanに含める。

対象は主に以下とする。

- public API
- interface
- 外部との境界になる関数・メソッド
- コンポーネント間でデータを受け渡す関数
- 責務や依存関係を理解するうえで重要な型

例:

```ts
onDidChange(
    listener: (uri: string) => void
): ConfigEventSubscription;
```

private helperや局所的な関数については、
原則として事前にシグニチャを決めない。

## 5. クライアントから見たAPIを確認する

主要な公開APIについて、

- クライアントが何をしたいAPIなのか
- その振る舞いを1つの公開操作で開始できるか
- 結果をクライアントから観察できるか

を確認する。

1つの振る舞いを実現するために
複数の公開APIを常に順番に呼ぶ必要がある場合は、

**本当に複数の公開操作として扱うべきか**

を検討する。

ただし、
テストのActを1行にすること自体を目的として
APIをまとめない。

実際のクライアントから見て自然かを基準にする。

## 6. Domain Logicと外部依存の分離を確認する

複雑なbusiness logicを追加・変更する場合は、

- immutableな入力から結果を求めるdomain logic
- 外部依存を扱うcontroller

へ自然に分離できるか確認する。

可能な場合は、

```text
Controller
    ↓
Domain Logic
    ↓
Result
    ↓
Controller
```

の構造を優先する。

Domain Logicは、
出力値ベーステストで検証しやすい形を目指す。

Controllerは、
mutableな共有依存を扱ってよいが
複雑なbusiness logicを持たせない。

ただし、
テスト可能性だけを理由に不要な層やinterfaceを追加しない。

# Test Designとの関係

Planではテストケースを設計しない。

Plan作成後、
`design-tests` によってクライアント視点からAPIと責務を検証する。

`design-tests` で、

- Actが不自然に複数の公開操作になる
- observable behaviorを検証する手段がない
- domain logicと共有依存が不自然に混在している

と判明した場合は、
実装開始前であればPlanを再検討する。

# 記述ルール

`.ai/templates/plan-implementation.md` のフォーマットに従う。

出力先は必ず以下とする。

`.ai/features/<feature-name>/tasks/<task-name>/plan-implementation.md`

各Plan項目は原則として、

**「<目的・理由>のため、<実装上の変更>を行う」**

という構造にする。

必要に応じて、
その直下に想定シグニチャを書く。

設計用語は必要に応じて使用してよい。

例えば、

- 抽象化する
- 分離する
- 委譲する
- インターフェースを導入する

などを一律に避けない。

ただし、
設計用語だけでは意図が分かりにくい場合は、
その設計判断によって何を変えたいのか具体化する。

避ける:

> ファイル監視を抽象化するため、インターフェースを導入する。

推奨:

> VSCode APIへの依存をアプリケーション側から切り離すため、`ConfigFileEventSource` インターフェースを導入する。

# Planの粒度

Planは短時間でレビューできることと、必要な実装変更が漏れなく具体化されていることを両立する。

Planを書く前に、タスク達成に必要な変更を実装作業の粒度で洗い出す。
同じ変更種別・意味を持つ作業は一つの項目にまとめ、異なる変更は目的が近くても別項目にする。
必要な変更が複数ある場合は項目数が増えてよい。簡潔さを理由に作業を省略したり、
「表示を追加する」「処理を更新する」のような抽象的な表現だけにまとめたりしない。

各項目には、必要に応じて変更する型・関数・引数・呼び出し関係・データ・状態・表示や出力を記載する。
Planを読んだ人が、何を追加・変更し、どこからどこへ値が流れ、処理や表示がどう組み立てられるかを説明できることを確認する。

# Planの扱い

Planは実装を拘束する仕様ではない。

一方で、
実装前に人間が理解した内容との比較基準として使用するため、
実装開始後に実装結果へ合わせてPlanを書き換えない。

実装前のレビューやテスト設計によって
方針自体を変更する場合は、
実装開始前にPlanを更新してよい。

実装開始後にPlanと異なる実装が必要になった場合は、
Planを維持したまま、
実装結果との差として扱う。

# 避けること

- コードを確認せずPlanを作る
- タスク記述をそのまま言い換える
- ファイル変更一覧をPlanにする
- 実装順序だけを書く
- 詳細な疑似コードを書く
- 必要な実装変更を省略し、private helperの名前や内部構成だけを先回りして固定する
- すべてのシグニチャを列挙する
- Planのシグニチャに実装を無理に合わせる
- テスト都合だけで公開APIを作る
- 出力値ベーステストを可能にすることだけを目的に不要な層を追加する
- 抽象化自体を目的にする
- 将来必要かもしれない設計を追加する
- 変更種別の異なる作業を、箇条書きの数を減らす目的で一つにまとめる
- 行番号や逐語的な編集手順を列挙する
- 実装開始後にActualへ合わせてPlanを書き換える

# 最重要原則

Planで決めるのは、

**実装の骨格**

までとする。

人間は、

- 目的
- 責務
- 境界
- 必要な実装変更の一覧
- データや状態の受け渡し
- 主要な想定シグニチャ

を理解する。

内部実装と具体的なテストケースは後段へ任せる。

Planは、

**実装前に理解するための地図であり、
実装を縛る設計書ではない。**

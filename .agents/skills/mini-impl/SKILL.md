# 目的

AI実装を、人間が短時間で確認できる小さなサイクルに分ける。

1. 現在の要求とコードを確認する
2. 次のmicrotaskを1件だけ提示する
3. 承認された範囲だけ実装する
4. 最小限の検証を行う
5. 実装後の状態から次のmicrotaskを決める

最初に全実装手順を固定しない。

# microtaskの基準

microtaskは、コード量ではなく

**人間が1回の判断で承認できる最小の設計上のコミットメント**

とする。

良い例:

- APIレスポンスを内部モデルへ変換できるようにする
- 変換結果をRepositoryから取得できるようにする
- Repositoryの値を画面へ表示する

悪い例:

- 関数を1つ作る
- ファイルを1つ編集する
- 20行変更する

以下を満たす単位を選ぶ。

- 目的が1つ
- 完了状態が明確
- 独立して検証できる
- 実装後も意味のある状態になる

コード量の目安は10-30行程度であるが、判断のしやすさを優先する。

# 手順

## 1. 現在状態を確認する

妥当なmicrotaskを決めるために必要な範囲でコードを読む。
質の良いmicrotaskを提示するためここは省略しない。
確認するもの:

- 既存の責務分割
- データや制御の流れ
- 利用できる既存API
- 関連テスト
- プロジェクトルール

## 2. 次のmicrotaskを提示する

ありうるmicrotaskを最大3案まで、箇条書きで提示する。
どのコンポーネントにどのような変更を加えるか、具体的な実装方針を最大3行程度で示す。

## 3. 実装する

承認されたmicrotaskだけを実装する。

以下は行わない。

- 関係のないリファクタリング
- 将来のためだけの抽象化
- 不要な汎用化
- 過剰なエラーハンドリング
- 次のmicrotaskの先取り
- テスト追加

既存アーキテクチャ、命名、設計方針を優先する。

## 4. 検証する

現在の変更に対応する最小限の検証を行う。

必要に応じて狭いものから実行する。

- 対象テスト
- 型チェック / compile
- lint
- 必要な範囲の追加テスト

## 5. 結果を報告する

以下だけを簡潔に示す。

### Result

- 実装した内容
- 実装時に想定していなかった問題

その後、実装後のコードを基準に次のmicrotaskを提示する。

# 人間の判断を求める条件
どんなに小さな仕様・設計・実装判断に対しても勝手にせず、プロンプトから自明なものを除き人間の判断を要求する。

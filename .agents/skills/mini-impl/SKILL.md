# 目的

ユーザーが指定したmicrotaskだけを実装する。

1件だけ指定された場合は、その1件だけを実装する。

複数件指定された場合は、指定されたmicrotaskを順番に実装する。

選択されていないmicrotaskは実装しない。

実装を便利にするため、コンパイルを通すため、完成形に近づけるため、といった理由で後続の変更を先取りしない。

# 基本原則

`mini-impl` は、機能を完成させるためのスキルではない。

**指定された小さな変更を、そのままコードへ反映するためのスキル**である。

たとえば指定されたmicrotaskが、

- `loadConfig` に `path: string` 引数を追加する

だけであれば、原則としてその変更だけを行う。

以下まで勝手に行わない。

- `path` を使ってファイルを読む
- 呼び出し元すべてを修正する
- 新しい型を追加する
- エラーハンドリングを追加する
- 関連コードをリファクタリングする

それらは別のmicrotaskで扱う。

# microtaskの粒度を維持する

指定されたmicrotaskが小さい場合、その小ささを維持する。

以下のような変更は、そのまま単独で実装してよい。

- 引数を1つ追加する
- フィールドを1つ追加する
- クラスのプレースホルダだけを作る
- メソッドのシグネチャだけを追加する
- 戻り値型だけを変更する
- 呼び出しを1箇所だけ追加する
- 値を1段先へ渡す
- 条件分岐だけを追加する

「これだけでは未完成だから」という理由で実装範囲を広げない。

# シナリオ順を尊重する

microtaskは、データ・制御の流れに沿って提示されている前提で扱う。

そのため、

- 呼び出し側を先に変更する
- 受け側はまだ変更しない
- 存在しないメソッドの呼び出しだけ先に追加する
- 戻り値を受け取る側だけ先に変更する

といった実装も許容する。

コード上の依存関係を理由に順番を入れ替えない。

# コンパイルエラーを許容する

指定されたmicrotaskを忠実に実装した結果、一時的にコンパイルエラーや型エラーが発生してもよい。

以下のような状態を許容する。

- 呼び出し側には新しい引数があるが、受け側にはまだない
- 新しいメソッドを呼び出しているが、まだ定義されていない
- interfaceだけ変更され、実装クラスがまだ追従していない
- 新しい戻り値を受け取っているが、呼び出し先はまだ返していない
- プレースホルダのため処理が未実装である

これらを解消するために、選択されていないmicrotaskを実装してはならない。

コンパイルが通らないこと自体を、このスキルでは失敗とみなさない。

# 許可する付随変更

指定されたmicrotaskそのものをコードとして成立させるために不可避な、機械的変更だけは同時に行ってよい。

例:

- 必要なimportの追加・削除
- formatterによる整形
- 名前変更に伴う同一宣言内の機械的修正
- 構文成立のために必要な最小限の記述
- プレースホルダの空実装や一時的な `throw` / `TODO` が、その言語上必要な場合の追加

ただし、

**「プロジェクト全体をコンパイル可能にするための変更」**

は不可避な付随変更とはみなさない。

対象microtaskの外側まで修正する必要がある場合は、その変更を行わず、一時的不整合として残す。

# プレースホルダ

microtaskでプレースホルダ追加が指定された場合、必要以上に実装しない。

たとえば、

- `ConfigLoader` クラスのプレースホルダを追加する

というmicrotaskなら、原則としてクラスを定義するだけにする。

将来必要になりそうな以下のものは追加しない。

- constructor
- field
- method
- interface実装
- factory
- エラーハンドリング
- コメント
- テスト

ただし、言語上クラス定義を成立させるために必要なものは追加してよい。

同様に、

- `load` メソッドのプレースホルダを追加する

なら、そのメソッドが存在する状態までに留める。

後続処理を推測して実装しない。

# 複数microtaskを指定された場合

複数件指定された場合も、それらを1つの機能実装として再解釈しない。

たとえば、

1. `submit` から `repository.search(inputText)` を呼ぶ
2. `search` に `query: string` 引数を追加する
3. `search` からHTTPクライアントへ `query` を渡す

が指定された場合、

1 → 2 → 3

の順で、それぞれ独立した変更として実装する。

3まで指定されていることを理由に、4以降のレスポンス処理などを追加しない。

指定順に明らかな誤りがない限り、順番も変更しない。

# 手順

## 1. 指定されたmicrotaskを確認する

ユーザーが選択したmicrotaskを特定する。

番号だけ指定された場合は、直前の `mini-suggest` の候補と対応付ける。

選択されたmicrotask以外は実装対象にしない。

## 2. 対象コードを確認する

microtaskを正しく実装するために必要な範囲だけコードを読む。

確認するもの:

- 対象箇所
- 現在のシグネチャ
- 周辺の呼び出し関係
- 関連する型
- プロジェクトルール

機能全体を再設計するための広範な調査は行わない。

## 3. 最小変更を決める

各microtaskについて、

**その文を満たすために必要な最小のコード変更**

を決める。

「このあと必要になるから」という理由の変更は含めない。

## 4. 指定順に実装する

複数件ある場合は指定順に実装する。

途中でコンパイル不能になっても、そのことを理由に後続の未選択microtaskを追加しない。

## 5. 差分を確認する

実装後、以下を確認する。

- 指定されたmicrotaskが実装されている
- 選択されていない変更を先取りしていない
- 関係のないリファクタリングが入っていない
- 不要な抽象化を追加していない
- microtaskの粒度を勝手に広げていない

この確認を最優先する。

# テスト・ビルド・静的解析

指定されたmicrotaskが非常に小さい場合、毎回プロジェクト全体のテストやビルドを通す必要はない。

特に、一時的な型エラーを許容しているmicrotaskでは、ビルド失敗は予想される。

以下の場合のみ、必要な検証を行う。

- ユーザーが明示的に指定した
- 選択されたmicrotaskだけで意味のある検証が可能
- 非常に軽量で、実装範囲を広げずに確認できる

検証を通すためにコードを追加修正してはならない。

# 避けること

以下は行わない。

- 選択されていないmicrotaskの実装
- 機能全体の完成
- コンパイルを通すためだけの追加実装
- 関係のないリファクタリング
- 将来のための抽象化
- 不要な汎用化
- 過剰なエラーハンドリング
- 頼まれていないコメント追加
- 頼まれていないテスト追加
- 周辺コードのついで修正
- 「こちらの方が設計としてきれい」という理由での変更拡大

# 出力

実装後は簡潔に報告する。

例:

> 実装しました。
>
> - 1: `submit` から `repository.search(inputText)` を呼ぶよう変更
> - 2: `search` に `query: string` を追加
> - 3: `query` をHTTPクライアントへ渡すよう変更
>
> 現在は `search` の呼び出し側との型不整合が1箇所残っています。後続microtaskで解消する想定です。

一時的なコンパイルエラーや未完成状態がある場合は、その事実だけを短く示す。

次に実装すべきmicrotaskを勝手に提案したり、そのまま実装したりしない。

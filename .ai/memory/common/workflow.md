# AIと実装を進めるときの好み

更新日：2026-10-03
状態：継続的な目的と、まだ試行中の具体的な方法を分けて記載。

## 継続して重視していること

- AIに実装を任せても、人間が実装方針と変更の意味を理解した状態でレビューしたい。
- 実装前に、どのような構成・責務・処理の流れにするかを短く把握したい。
- 実装後は、事前に理解した方針と実際の変更との差を追いやすくしたい。
- 実装Planでは、振る舞いの説明だけでなく、必要な実装変更を実装レベルで漏れなく列挙したい。引数追加、関数定義、データ受け渡し、状態更新、表示構成など、同じ意味・変更種別の作業だけをまとめ、異なる作業は分ける。行番号単位の編集指示は求めていない。
- 作業は、人間が理解・確認できる意味のある単位に分けたい。
- 変更理由、影響範囲、検証結果をコードと対応付けて把握したい。
- AIの説明だけで納得するのでなく、実際の差分やテスト結果などの証拠を確認したい。
- 手順書・ルール・ファイル更新に手間がかかり、実装のテンポが落ちることは避けたい。

## この好みを作業に反映する際の目安

以下は上記の目的から整理した運用上の目安であり、固定の承認フローではない。

- 実装方針は、主要な責務と処理の流れが分かる程度に短く示す。
- Planでは、必要な変更事項を具体的な作業に分解してから、同じ意味・変更種別ごとにまとめる。簡潔さのために別種の作業や必要事項を省略しない。
- 実装中に方針が変わった場合は、変わった点と理由を説明する。
- 変更の説明は、ファイル名の列挙だけで終わらせず、何を実現する変更かが分かるようにする。
- 詳細な理解が必要な箇所では、変更箇所に加え、それを意味づける周囲の制御・関数・呼び出しの流れを説明する。
- すでに依頼された範囲の作業に、新しい承認待ちを機械的に追加しない。今回指定された進め方に従う。

## 検討中：既定のルールにはしない

| 検討事項 | 現在分かっていること | まだ固定しないこと |
| --- | --- | --- |
| microtaskによるrapid-implementation | 人間が短時間で理解できる小単位で進める方法を試している | 全タスクを必ずmicrotask化すること |
| 30秒程度で確認できる粒度 | 関数単位でも粗い場合があり、意味のある処理単位で確認したい | 一律の時間制限や行数制限 |
| 手順選択と承認 | ユーザーが手順を選び、保存する方法を検討・実装依頼した | 全工程で必ず承認待ちにすること |
| 理解・設計力の維持 | AIのコードを説明できても、仕様変更に自力で対応できるとは限らないと問題意識を持っている | 学習目的のために毎回人間へ実装を戻すこと |

## 根拠

- 2026-09-19〜25のコードレビュー支援に関する会話：変更理由、周囲の文脈、影響、証拠を短時間で確認したいという目的。
- 2026-09-27前後の実装フローの会話：実装前の方針理解と、実装後の予想との差の確認を重視。
- 2026-09-30〜10-01「AI開発の設計力維持」「品質保証の未来価値」：理解・設計・変更対応の能力について問題提起。
- 2026-10-01「AI実装手順の設計」：30秒程度で確認できるタスクへの分割、CLI・スキル・手順保存を検討。ファイル編集の手間によるテンポ低下を指摘。
- 2026-10-02「Rapid Implementation助言」：microtaskを使う進め方について継続して相談。
- 2026-10-03「Planの実装粒度」：Planにはすべての必要な実装変更を列挙し、同じ意味の作業のみ統合するよう明示。振る舞いの説明やクライアント可視性だけでは実装作業の記述として不足する、と訂正。

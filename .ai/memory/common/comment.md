# コメントとコードの説明

更新日：2026-10-03
状態：初期のWhy中心の方針に、後から示された処理ブロックの説明への要望を反映。

## 何を説明するか

- コメントは、人間がコードを理解する時間を短くするために書く。
- まず命名・関数分割・型・データ構造で意図を表せないかを検討する。
- 複数行を読み解かないと分からない処理は、意味のあるブロックごとに「何をしているか」を短く要約してよい。
- 設計判断の理由、制約、非自明な前提も必要に応じて説明する。
- Whyだけに限定しない。一方で、各行の逐語訳や、名前から明白な内容の繰り返しでコメントを増やさない。
- 入力・出力・前提が理解の鍵になる場合は、それを具体的に示す。

## 日本語の書き方

- 自然な日本語で書く。`natural-expression` スキルが利用できる環境では、コメントの日本語を整えるために使用する。
- 対象同士の関係だけを述べて、実際の動作が分からない表現を避ける。
- コードや仕様を確認し、「呼び出す」「値を渡す」「購読する」「通知する」「表示する」「解除する」など、実際の動作を表す。
- 「接続する」「連携する」などの語を一律に禁止しない。その語で動作が明確に伝わるかを判断する。

例：

- 動作が分かりにくい：「設定ファイルの作成・更新を通知へ接続する」
- 動作が分かる：「設定ファイルの作成・更新時に通知する」

## コメント量と置き場所

処理ブロックを説明するコメントは好むが、コメント過多や、コメントに頼ってコードが分かりにくいままになることは懸念している。説明が必要な箇所に絞る。

エディタにだけ説明を表示し、ソースコードには保存しない方法も検討されている。ただし、これは全プロジェクトに適用する採用済みルールではない。

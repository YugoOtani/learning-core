# コードの書き方

更新日：2026-10-03
状態：過去に明示された好みを中心に整理。

## 変更範囲と最小実装

- 現在の要求を満たす、最小限で一貫した変更にする。
- 既存の構成、責務、命名規則、コードスタイルを確認してから実装する。
- 関係のないリファクタリングや整理を混ぜない。
- 将来必要になるかもしれないだけの抽象化、拡張ポイント、汎用化を追加しない。
- 今回考慮しなくてよいケースのために、細かなエラーハンドリングや分岐を増やさない。
- 最小実装は「行数を最少にする」という意味ではない。要求を満たし、人間が理解できる構成を保つ。

エラーハンドリングを一律に省略する好みではない。現実の入力・失敗条件や要求に必要な処理と、将来の可能性だけを理由にした処理を区別する。

## 責務と関数分割

- 1つの関数には明確な責務を持たせる。
- 意味のある処理単位は、役割が分かる名前付き関数へ切り出す。
- 単に行数を減らすためだけの関数分割は行わない。
- 意図は可能な限り、命名・関数分割・型・データ構造によって表現する。
- コメントを書けば理解できるという理由で、分かりにくい構造を放置しない。

## 根拠

- 2026-09-21〜22「アプリ候補比較」「PoCアプリとCoding Agent比較」周辺：既存のCoding Guidelinesとして、既存設計の尊重、無関係な変更の禁止、将来だけの抽象化の禁止、意味のある関数分割を提示。
- 2026-10-02「最小実装の指定方法」：細かなエラーハンドリングや今回不要なケースを含む冗長な実装への不満を明示。
- 「最小実装」の適用範囲に関する補足は、上記の意図を一律の例外処理禁止に広げないための整理。
